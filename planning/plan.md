# Choices

- **Runtime:** Python 3.11 or later (implementation environment: Python 3.12) with stdlib `argparse`, `sqlite3`, `concurrent.futures`, `urllib.request` and `unittest`, plus `jsonschema` pinned with transitive dependencies and hashes in `requirements.lock`; this keeps the operator setup small while validating the supplied schema with an established validator.
- **Interface:** a CLI, `python3 -m access_intake`, backed by one local SQLite database shared by overlapping processes on the same host, as the user selected; short transactions and independent reads let reviewers inspect completed work during intake.
- **Test command:** `env -u API_KEY python3 -m unittest discover -s tests -v`; it extends the repository's starter command, uses temporary state, rejects real sockets and requires no external credentials.
- **Model provider:** a configurable adapter makes a non-streaming HTTPS `POST https://api.openai.com/v1/responses` with `urllib.request`, model `gpt-4.1-mini`, instructions plus the decoded message as data, and `text.format` JSON Schema output; a saved-reply adapter implements the same boundary for all tests and development commands, so provider integration is testable offline. The endpoint/model are configurable; the real adapter reads `API_KEY` only when explicitly selected. Request and completion/refusal handling follow the official [Responses reference](https://developers.openai.com/api/reference/resources/responses/methods/create), [Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs), and [model reference](https://developers.openai.com/api/docs/models/gpt-4.1-mini).

This is a plan only. No application code, tests, response fixtures or deliverables are created in this task. File paths, commands and test IDs below are proposed implementation contracts, not existing capabilities or reported test results. `planning/spec.md` remains the committed 240-line spec. The 12-scalar accuracy convention and operational settings below are design choices, not additional claims about the source requirements.

The user clarified two ambiguous source cases: **U-01**, a withdrawal missing request_id or request_date must fail gracefully with a clear error; **U-02**, an impossible calendar date must fail gracefully with a clear error. Validate them before routing and use the policy's standard error envelope: `status=error`, `owner=IT Service Desk`, `next_action=retry-extraction`, `extraction=null`, with a diagnostic identifying the source fact to correct before retrying. These decisions resolve spec Open question 13's incomplete-withdrawal case and question 10's impossible-date case; partly specified dates remain open. Valid reversed dates such as IT-014 still follow policy rule 3. Both clarified cases have their own test-plan rows.

## Proposed operating contracts

Use flat input directories and unique basenames as document IDs; reject colliding/nested inputs with an explicit input diagnostic rather than silently renaming or merging. Keep original source bytes in durable state. Store immutable attempts, source revisions, configuration fingerprints and policy versions separately from current-result pointers; queue and extraction views read the same committed attempt. Pending/leased/retry-wait states belong to work records, not fabricated successful deliverable extractions.

Assign a monotonically increasing revision sequence transactionally when a source revision is accepted. A compare-and-swap update prevents an older in-flight revision from overwriting a newer accepted revision; do not use exported_at to order business revisions. Repeated successful input with the same extraction/routing fingerprints reuses results. An explicit retry targets a saved attempt/source/configuration and bypasses reuse. An ordinary rerun keeps failed records visible; `retry` or `resume` handles failed or unfinished work explicitly. Policy-only routing changes reuse validated extraction but create a new versioned routing result; extraction-affecting changes refresh extraction. Fingerprints include provider/endpoint, model, effective model options, prompt bytes, schema bytes and policy/routing version, never credential values. Retain all attempts for this exercise; SQLite history is logically separate from current views and exported files.

Default to four workers, a configurable local request-rate limiter, a 30-second request timeout and at most three total transient-error attempts with bounded exponential delay honoring Retry-After within an overall deadline; use a fake clock in tests. Refusal, invalid output and semantic validation failures are visible errors requiring explicit retry after correction. Use transactional worker leases and idempotent persistence: a response received but not committed may require another provider call after a crash; a committed completion is reused. These are declared operating choices to document and verify, not throughput promises. The 200–400 ordinary / roughly 2,000 peak messages describe the workload; record measured limits only after implementation. SQLite supports this user's selected same-host scope, not cross-host or network-filesystem coordination.

Publish exports from a single database snapshot into a new generation directory; commit publication with an atomic generation pointer. Expose `deliverables/extractions.jsonl` and `deliverables/queue.json` through the selected generation and tell readers to resolve the generation once when reading both files. History remains in state storage. Tests must cover a crash between staging and publication and a reader spanning publication; independently opening two paths across a generation switch is not a promised coherent read.
